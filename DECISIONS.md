# DECISIONS.md — skills-toggle

One line per material decision: what + why. Newest last.

Entries D1-D39 are historical through v3.0. D40 and later plus
`IMPLEMENTATION_PLAN.md` supersede earlier scope and UX choices when they
conflict; established safety and file-format facts remain in force.

- **D1 — Docs verified live, treated as authoritative.** Downloaded the Desktop Plugin SDK doc (938 lines) from the hermes-agent repo, fetched the plugins user-guide + example-plugins repo, and read the local template at `~/.hermes/skills/autonomous-ai-agents/hermes-agent/templates/plugin.js` plus the real desktop SDK source at `~/.hermes/hermes-agent/apps/desktop/src/sdk/index.ts` to confirm component props (Switch/Badge/StatusDot/EmptyState/ErrorState/SearchField/ConfirmDialog/SegmentedControl/Skeleton/PaletteContribution). No guessing against the SDK.
- **D2 — This Pro is NOT canonical; nothing real was mutated.** The brief said `~/.hermes` here is mostly empty — it is actually a full live install. All reads were reference-only; every mutation test runs against `/tmp` fixtures. The Air's layout (via the brief) plus verified conventions here drive the design.
- **D3 — `skills.disabled` stores BARE skill names.** Verified in the live `config.yaml` (`- airtable`, `- apple-notes` …), not `category/name`. The hermes tool therefore matches membership by bare name, matching hermes' own semantics.
- **D4 — No PyYAML, no fastapi in system python3.** Backend core is dependency-free (stdlib only); the FastAPI router layer is import-guarded so the file imports cleanly for tests while still exporting `router` inside the gateway process (which has fastapi). YAML edits use a surgical line-level editor (preserves user comments/formatting) + timestamped backup, validated by re-parse after edit.
- **D5 — Unified package layout exactly per SDK doc "One package, both SDKs".** `~/.hermes/plugins/skills-toggle/{plugin.yaml, dashboard/{manifest.json, plugin_api.py}, desktop/plugin.js}`. manifest.json is exactly `{"name": "skills-toggle", "api": "plugin_api.py"}` per doc + brief; no web-dashboard tab fields (this plugin targets the native desktop pane, and a tab declaration without an entry bundle would be broken).
- **D6 — Desktop half ships `defaultEnabled: false`.** SDK doc: unified-package desktop halves default to off, inventorying in Settings → Plugins until toggled. Matches the brief's enable gates.
- **D7 — Symlink convention: absolute targets, flat names.** Matches the verified existing convention in `~/.claude/skills` (`airtable -> /Users/bakirmousa/.hermes/skills/productivity/airtable`). Link name = skill name.
- **D8 — Tool taxonomy.** Per-tool per-skill state ∈ `enabled | missing | broken-link | foreign-link | unmanaged-dir`; tool dir absent → tool-level `absent` (offer create-dir-and-link). hermes tool state ∈ `enabled | disabled` (config membership). `foreign-link` (symlink pointing outside our skills tree / at another skill) is refused for both toggle-off and overwrite — reported, never silently re-pointed.
- **D9 — Safety: never delete skill source dirs, real dirs, or foreign links.** Only symlinks whose resolved target is inside the managed skills root are ever removed; real dirs and foreign links produce explicit errors. Uninstall removes only the plugin folder.
- **D10 — ZCode tool dir default `~/.agents/skills`, fallback `~/.zcode/skills`.** Detected on this machine: ZCode user skills load from `~/.agents/skills`. Runtime detection prefers an existing `~/.agents/skills`, else `~/.zcode/skills`; overridable via config JSON (see README).
- **D11 — Hermes home resolution order:** `$HERMES_HOME` > `$HERMES_PROFILE` → `~/.hermes/profiles/<name>` > `~/.hermes`. All paths resolved via env/`~`; zero hardcoded absolute paths in code.
- **D12 — Tool target-dir map:** defaults in code, overridable via `<hermes_home>/skills-toggle.json` (survives plugin updates; never inside the plugin dir). Supports `~` and `${VAR:-default}` expansion (`OPENCODE_CONFIG_DIR` honored by default for opencode).
- **D13 — Hermes config edits: surgical text edit, not PyYAML round-trip.** `hermes config set` exists but its list semantics for `skills.disabled` are undocumented; a dump-based rewrite would clobber user comments. Every config.yaml mutation writes a timestamped backup first (`config.yaml.bak.skills-toggle.<ts>`).
- **D14 — Mutation log lives in the plugin folder** (`data/mutations.log`, JSONL, gitignored) — inside the pre-approved write scope; avoids inventing new write locations under `~/.hermes`.
- **D15 — Username discrepancy noted.** Brief said "user bz"; this machine's home is `/Users/bakirmousa`. Irrelevant to the artifact: everything resolves home dynamically.
- **D16 — Caching.** `/state` scans are cached server-side; signature = mtimes of skills root + category dirs + config.yaml + each tool dir (+ config-override mtime), plus a generation counter bumped on every mutation. TTL 2s guards against same-mtime edits. `/state` payload is lean (descriptions truncated to 160 chars); full SKILL.md text only via `GET /detail`.
- **D17 — Repo remote:** `qwertyuiop97/skills-toggle` verified private + empty; push over HTTPS with existing `gh` credentials.
- **D18 — GitHub sync incident (autosync).** First `git push` was rejected: an external autosync mechanism on this machine had already pushed local history to `qwertyuiop97/skills-toggle` (commit `164e717 autosync`, an auto-generated README) while the build ran. Resolution was fix-forward per the ground rules: fetched, rebased the two newer local commits onto `autosync` (no history rewrite, no force-push), kept the finished README, pushed clean. Lesson applied: attempt the first push right after the initial commit so remote drift surfaces early.
- **D19 — Headless-serve 404 diagnosed from source; gateway restart left to the user.** The live pane 404'd with the headless message: `hermes serve` (the desktop's backend) mounts plugin API routes at startup only, and this gateway predates the plugin's enablement. Verified in hermes source (web_server.py `_mount_plugin_api_routes` + `_plugin_api_runtime_gate`; rescan only refreshes the plugin list, it does not mount routers). A gateway restart touches live services (Telegram/Photon connected) and sits outside the pre-approved read-only `hermes` scope, so the pane now maps this exact error to the remedy ("run `hermes gateway restart`, then Retry") and README documents it — one command for the user or their Hermes agent.
- **D20 — Preset scope:** presets are CROSS-TOOL with per-tool checkboxes in the confirm dialog (default: all present link tools); apply is ADDITIVE-enable only, except the built-in "Minimal" preset which disables all consumer links. Additive default honors the opt-in constraint; "replace" mode is deferred (would need a dry-run diff UI first).
- **D21 — Preset file schema (shareable):** `{"version": 1, "name": str, "skills": ["category/name", …], "tools": ["tool-id", …]}`. Apply = for each listed tool, enable listed skills (additive). Unknown skill ids on import are skipped and reported; unknown tool ids are dropped. Version field gates forward-compat.
- **D22 — New-skill detection:** no filesystem watcher exists in the SDK; the pane diffs successive `/state` snapshots (15 s poll already in place) against a seen-set persisted in `ctx.storage`. Batch arrivals produce ONE prompt listing all new skills, never N prompts.
- **D23 — Auto-link granularity:** per-tool boolean, stored in `ctx.storage`, opt-in via the arrival prompt ("always for this tool") and clearable in the onboarding panel. Category-level filtering deferred.
- **D24 — Responsive breakpoints (container-measured, not viewport):** the pane measures its own width with a ResizeObserver (viewport media queries are wrong for dockable panes — the v1 bug). narrow <360 px: 2-col tool grid, descriptions hidden, filter chips scroll horizontally; medium 360–559 px: 3-col grid; wide ≥560 px: 3-col grid with roomier spacing. Default pane width stays 320 px, now fully usable.
- **D25 — Health chip thresholds:** chip hidden when healthy; muted badge "N unlinked" when only unlinked; warn badge "N broken" takes precedence when broken links exist. Click navigates to `/skills-toggle`. No red tier in v2 (foreign/unmanaged already surface in the pane's Issues view).
- **D26 — Agent auto-detect:** dir-existence only (config-file sniffing and PATH probing are flaky and agent-versions churn). Precedence: skills-toggle.json override > detected existing dir > built-in default (ZCode keeps its two-candidate fallback). Custom agents are added as label+dir pairs written to skills-toggle.json via the new /config/tools route (backed up first).
- **D27 — Grok skills dir is real:** verified on the reference machine during v1 recon (`~/.grok/skills` with ~69 links). Not speculative.
- **D28 — ZCode "detect":** candidates `~/.agents/skills` then `~/.zcode/skills` (first existing wins; overridable via skills-toggle.json). Symlink support assumed (POSIX); Windows gets junction-style symlinks via os.symlink (may require developer mode — documented limitation).
- **D29 — Undo (Added A):** implemented as an in-pane undo banner with a 30 s countdown holding the inverse mutation set (per-skill, per-tool, prior states) — not a toast action, because the SDK toast `action` payload shape is unverified. Undo calls the same toggle route (respecting all refusal rules).
- **D30 — Dry-run (Added B):** every bulk/preset apply confirms with computed counts + the first 5 affected skills, computed client-side from the current cached state. Full link-by-link diff view deferred to the import wizard where it matters most.
- **D31 — Drift pull direction:** v2 drift is detect + "push canonical out" (backup tool copy, replace with symlink). "Pull external in" writes the external version to category `imported/` only when that name is free; same-name pull is reported, not merged (no merge algorithm in v2).
- **D32 — MCP/connectors tab (#12) is out of v2 scope:** per-app config writers (config.toml, extensions, json) each need their own schema-versioned, atomic-write, tested module — the brief itself ships it after the skills surface stabilizes. Filed in QUESTIONS_FOR_HERMES.md for scoping.
- **D33 — Beginner success metric:** time-to-first-enabled-skill (empty state → first successful toggle) and zero-unprompted-enables (hard invariant, tested). Recorded in README.
- **D34 — Q1 resolved (a): MCP tab built for Hermes + Claude Desktop first.** Hermes `mcp_servers` (config.yaml) is the catalog; entries carry an `enabled:` field (verified live: chrome-devtools). Hermes toggle = surgical edit of that field (backup + re-parse self-check, same pattern as skills.disabled). Claude Desktop toggle = entry present/absent in `claude_desktop_config.json` (macOS `~/Library/Application Support/Claude/`, Linux `~/.config/Claude/`, Windows `%APPDATA%\Claude\` — first existing candidate wins). Catalog projection for Claude = universal keys only (`command`, `args`, `env`, `url`, `headers`); `enabled` and hermes-specific keys are stripped. Drifted = same name, different projection; syncing overwrites (backup first), removing a drifted entry requires explicit confirmation (force). Foreign entries (in Claude, not in catalog) are listed and never touched. Codex/OpenCode writers deferred until their config.toml/json writers are schema-tested.
- **D35 — Q2 resolved (b):** distribution stays deep-link only (`hermes://plugin/install?repo=…`); no community-index submission.
- **D36 — Q3 resolved (b):** ship without a demo GIF.
- **D37 — Q4 resolved (a):** presets remain local built-ins + shareable file format (as shipped); no community feed.
- **D38 — Q5 resolved (b):** dual-gate stays notice-only (the pane's gateway-restart remedy), no core-side change.
- **D39 — version drift fix:** the 2.1.0 bump missed `plugin.yaml` (only the code constant changed), so the two manifests disagreed after the v2.1 increment. Both now bump together in the same commit; caught during the MCP-tab version bump.
- **D40 — Stabilization is tool-first.** The default experience becomes a tool overview with counts and bulk entry points because the current 100+ skill matrix is too dense for the Hermes split layout. The full matrix remains an optional expert view on sufficiently wide surfaces.
- **D41 — Compact pane and workspace have different jobs.** The contributed side pane is a status/shortcut surface; the `/skills-toggle` workspace is the complete Control Center. Both must remain usable if Hermes exposes only the pane or cannot open the workspace programmatically.
- **D42 — Hermes stays canonical.** First-run discovery may scan known or owner-added folders, but those locations are import/adoption sources or tool targets, not competing canonical stores. Every adoption operation is previewed before mutation.
- **D43 — Backend-authored bulk plans supersede D30's client-only preview.** Bulk operations return exact affected, unchanged, protected, and failed item ids; apply consumes a reviewed plan or equivalent validated request, records a receipt, and provides precise undo/restore guidance.
- **D44 — Autonomous execution with a material escalation threshold.** Hermes decides routine implementation, copy, layout, and test details from repository evidence and may use configured bots or independent review without requiring MOA consultation. It contacts the owner only for unresolved choices that materially change product behavior, canonical storage, compatibility/public APIs, safety/data-loss boundaries, permissions/secrets/external publishing, or irreversible/destructive actions; non-blocking questions never pause safe work.
- **D45 — Model routing is capability-based and token-aware.** A fast main orchestrator such as DeepSeek Flash is acceptable; stronger specialists handle architecture, difficult debugging, filesystem safety, and independent review, with Grok 4.6 used for the required challenge reviews. Context and test runs stay bounded, but token savings never waive acceptance, safety, accessibility, or live-Hermes evidence.
